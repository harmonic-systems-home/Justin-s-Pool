## Architecture notes (read first)
- **Single source of truth:** one config object (schedules, rates, volumes, valve settings, measured values). All tabs render from it. Commissioning results WRITE INTO it — e.g., a measured Watts@RPM overrides the affinity-law estimate everywhere; a measured BTU populates the gas model; measured split-f updates turnover math.
- **Clock-offset model (from test 17):** schedules are stored EXACTLY as programmed on the device (pump-clock times, as photographed — the ground truth of the settings), and the config carries **four explicit clock offsets, one per pad clock**, each with value + audit date + evidence photo ref:
  - `intelliflo`: ≈ −10 h 00 m (audited 7/26/26, two photos a week apart)
  - `suntouch`: ≈ −10 h 00 m (observed 7/17/26: 2:26 AM displayed at 12:26 PM — same outage signature)
  - `intermatic_left`: ≈ −12 h (observed 7/18/26: pointer at 12 nite at ~12:30 PM; moot for actuation while tripper-less, recorded for completeness — and a nonconforming offset is itself data: −12 h ≠ −10 h suggests it was hand-set wrong rather than outage-reset)
  - `intermatic_right`: ≈ 0 (observed 7/18/26: correct)
  Real-world times are always DERIVED (programmed + that device's offset), never stored. The Daily tab shows both: the settings card displays device-clock times verbatim next to each offset ("IntelliFlo clock: 10 h behind, audited 7/26"), while all bar-chart timelines and the Costs computation run in REAL time. TOU cost placement uses real times exclusively — this is what reveals the current 3250 run straddling the 5–8 PM peak. When R5 zeroes the offsets, derived = programmed and the offset banners clear; the History log keeps old offsets with dates. Test 17 re-audits refresh all four after any outage.
- **Estimated vs measured provenance:** every number carries a badge (EST / MEASURED + date). Commissioning is the mechanism that flips badges. This is the app's core discipline.
- **Persistence architecture (two tiers, same JSON contract):**
  - **Storage of record:** a separate PRIVATE repo (`Justin-s-Pool-data`) holding `results.json` — keeps commissioning data private while the app repo/Pages stay public+free (private-repo Pages would require a paid plan). Every save = a commit → history, diffs, attribution ("recorded by" name field goes in the commit message).
  - **Tier 1 (Justin, zero-GitHub):** Cloudflare Worker (free tier) holds ONE fine-grained PAT (Contents-only, data repo) as a secret; endpoints GET/PUT `/data` proxy the GitHub Contents API (fetch SHA → merge → PUT); CORS locked to the Pages origin; auth = shared passphrase header, entered once per device, remembered in localStorage. Justin's onboarding: "type the pool password." Annual token rotation happens once, at the Worker, by Rick.
  - **Tier 2 (Rick, direct/admin):** same JSON contract straight to the GitHub API with a personal fine-grained PAT pasted into a settings field (localStorage). Fallback if the Worker is ever down.
  - **Roles — two passphrases, scoped at the Worker:** FAMILY passphrase = full (write all namespaces + read sensitive fields). CONTRACTOR passphrase = write the `visit-log` namespace + read public only — **specifically cannot read sensitive fields (the redacted fee is the contractor's own; the role exists so he can log work without seeing what other workers would see either).** Worker branches on which passphrase authenticated.
  - **Public/private data split:** non-sensitive config (schedules, measurements, volumes) may sync via either tier and cache in localStorage freely. Fields marked `sensitive` (e.g., pool-guy fee) are served ONLY on family-authenticated requests and cached ONLY on devices where that passphrase is stored — the public bundle, unauthenticated sessions, and contractor sessions never contain them.
  - localStorage remains the working copy; Sync is semi-automatic (debounced auto-save after each commissioning result + manual Sync button). Conflict handling: stale SHA → 409 → refetch, merge (results are per-test, so merges are disjoint), retry.
- **Active vs proposed schedule:** Costs tab reads the ACTIVE schedule; What-If holds the draft. A "promote to active" action (with confirmation + History log entry) formalizes a reprogram.
