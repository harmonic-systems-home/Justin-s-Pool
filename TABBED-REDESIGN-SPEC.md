## Motivation
Single-page layout is saturated. Reorganize into a tabbed interface where each tab serves a distinct reader mode: operating (daily), servicing (maintenance), understanding (design/history), deciding (costs/what-if), and verifying (commissioning).

## Architecture notes (read first)
- **Single source of truth:** one config object (schedules, rates, volumes, valve settings, measured values). All tabs render from it. Commissioning results WRITE INTO it — e.g., a measured Watts@RPM overrides the affinity-law estimate everywhere; a measured BTU populates the gas model; measured split-f updates turnover math.
- **Clock-offset model (from test 17):** schedules are stored EXACTLY as programmed on the device (pump-clock times, as photographed — the ground truth of the settings), and the config carries **four explicit clock offsets, one per pad clock**, each with value + audit date + evidence photo ref:
  - `intelliflo`: ≈ −10 h 00 m (audited 7/26/26, two photos a week apart)
  - `suntouch`: ≈ −10 h 00 m (observed 7/17/26: 2:26 AM displayed at 12:26 PM — same outage signature)
  - `intermatic_left`: ≈ −12 h (observed 7/18/26: pointer at 12 nite at ~12:30 PM; moot for actuation while tripper-less, recorded for completeness — and a nonconforming offset is itself data: −12 h ≠ −10 h suggests it was hand-set wrong rather than outage-reset)
  - `intermatic_right`: ≈ 0 (observed 7/18/26: correct)
  Real-world times are always DERIVED (programmed + that device's offset), never stored. The Daily tab shows both: the settings card displays device-clock times verbatim next to each offset ("IntelliFlo clock: 10 h behind, audited 7/26"), while all bar-chart timelines and the Costs computation run in REAL time. TOU cost placement uses real times exclusively — this is what reveals the current 3250 run straddling the 5–8 PM peak. When R5 zeroes the offsets, derived = programmed and the offset banners clear; the History log keeps old offsets with dates. Test 17 re-audits refresh all four after any outage.
- **Estimated vs measured provenance:** every number carries a badge (EST / MEASURED + date). Commissioning is the mechanism that flips badges. This is the app's core discipline.
- **Persistence architecture (two tiers, same JSON contract):**
  - **Storage of record:** a separate PRIVATE repo (`Justin-s-Pool-data`) holding `results.json` — keeps commissioning data private while the app repo/Pages stay public+free (private-repo Pages would require a paid plan). Every save = a commit → history, diffs, attribution ("recorded by" name field goes in the commit message).
  - **Tier 1 (Justin, zero-GitHub):** Cloudflare Worker (free tier) holds ONE fine-grained PAT (Contents-only, data repo) as a secret; endpoints GET/PUT `/data` proxy the GitHub Contents API (fetch SHA → merge → PUT); CORS locked to the Pages origin; auth = shared passphrase header, entered once per device, remembered in localStorage. Justin's onboarding: "type the pool password." Annual token rotation happens once, at the Worker, by Rick.
  - **Tier 2 (Rick, direct/admin):** same JSON contract straight to the GitHub API with a personal fine-grained PAT pasted into a settings field (localStorage). Fallback if the Worker is ever down.
  - **Roles — two passphrases, scoped at the Worker:** FAMILY passphrase = full (write all namespaces + read sensitive fields). CONTRACTOR passphrase = write the `visit-log` namespace + read public only — **specifically cannot read sensitive fields (the redacted fee is the contractor's own; the role exists so he can log work without seeing what other workers would see either).** Worker branches on which passphrase authenticated.
  - **Public/private data split:** non-sensitive config (schedules, measurements, volumes) may sync via either tier and cache in localStorage freely. Fields marked `sensitive` (e.g., pool-guy fee) are served ONLY on family-authenticated requests and cached ONLY on devices where that passphrase is stored — the public bundle, unauthenticated sessions, and contractor sessions never contain them.
  - localStorage remains the working copy; Sync is semi-automatic (debounced auto-save after each commissioning result + manual Sync button). Conflict handling: stale SHA → 409 → refetch, merge (results are per-test, so merges are disjoint), retry.
- **Active vs proposed schedule:** Costs tab reads the ACTIVE schedule; What-If holds the draft. A "promote to active" action (with confirmation + History log entry) formalizes a reprogram.

- **Drain & fill:** cartridge-filter system → NO backwash/waste port on the pad; draining requires a submersible utility pump in the deep end, discharging to a **sanitary sewer cleanout** (CA rule: pool water to sewer, never storm drain/gutter — Sacramento-area districts enforce). Main pump cannot pump the pool down (loses prime below skimmer). **Never fully drain casually** — empty gunite shells can float/crack from groundwater (hydrostatic pop-out); full drains are deliberate, pro-supervised events. Realistic use: partial drain-and-refill (1–2 ft) for CYA management — pool-guy territory. Filling: hose over coping or the dedicated fill line (see Commissioning test 13); watched, no autofill installed.
- **Routine care calendar (the tab's centerpiece — populated by Commissioning test 15):** a who/what/how-often table splitting every recurring task between POOL SERVICE and JUSTIN, with seasonal variants (normal vs dirty season). **Anchor chore: surface skimmer robot — charged every other day, and the recharge ritual IS the emptying ritual (its battery enforces its own maintenance cadence).** The robot is the system's first interceptor in a defense-in-depth chain (surface bot → skimmer baskets → bottom robot → cartridge filter → heater flow switch); it catches needles before they waterlog and sink, which is why it relieved every downstream layer when added. Other rows: skimmer basket(s) + pump strainer emptying (much lighter since the surface bot; cadence per test 15 interview; peak needle-drop months still serious); bottom robot deploy/recharge cycle; floater tablet refill; filter-gauge glance (delta from clean baseline); spa-level glance (split-drift monitor); **Polaris hose vacuum = SURGE CAPACITY, not routine — deployed with the booster dogs only when the two robots can't keep up (Tier 2; trigger + calendar per test 16)**. The tab shows the 12-month debris-load strip once test 16 characterizes it. Each row: task, owner, cadence, season notes, last-done date field.

### 4. Costs
Reads ACTIVE schedule. Electric: per-window kWh from Watts curve (measured points override affinity estimates), SMUD TOD rates incl. segregated midnight–6 AM EV band (editable seasonal rate table), $/day and $/mo. Gas: heater BTU (badge EST until commissioned), $/therm (editable), $/hr firing, $/session (egg-timer durations), °F-per-session. **Sensitive-field redaction model:** some values (pool-guy monthly fee now; extensible to any competitively/personally sensitive number) are marked `sensitive` and live ONLY in the private data repo — never in the public app bundle, public repo, or localStorage of unauthenticated devices. Redaction is **by absence**: the Worker returns sensitive fields only on passphrase-authenticated requests, so an unauthenticated browser never receives them (view-source-proof, not CSS-hidden). Locked UI shows the row as "🔒 unlock to view" and excludes it from totals with a label. This makes the URL safely shareable with the pool guy and other workers: full design/operation/commissioning visible, competitive costs invisible. The passphrase thus gates both write-sync AND private-read — one secret, two privileges, fine at this trust scale.

### 6. Commissioning
Each test = procedure card + recordable result fields (value, date, who) that write into config with MEASURED badges:
1. **Gas meter clocking** — heater BTU input: all other gas off, time test-dial rev; BTU/hr = 3600/sec × dial-ft³ × ~1,030. → gas model
2. **Heater cabinet measurement** — width vs BTU ladder (~21"=150k … 36"=400k) as cross-check; also check inside front access door + gas valve label for plates
3. **Watts per configured speed** — read live Watts off the IntelliFlo display at each programmed RPM (start the speed, let it stabilize ~30 s, record). Table to fill: **1350 = 136 W (MEASURED 7/20/26)** · 2600 (proposed turnover) · 3000 (Speed 2) · 3030 (Speed 4 manual) · 3250 (Speed 1) · **3450 = 2,398 W (MEASURED 1/26/2024, during a Quick Clean run; filter state that day unknown — Watts at fixed RPM varies somewhat with hydraulic load, so re-confirm when convenient).** Cube-law validation: 136 W @1350 predicts 2,269 W @3450 — measured lands +6%, excellent; interpolated 3250 ≈ 2,005 W. Heating-run electricity now real: 3 h 10 m × ~2.4 kW ≈ 7.6 kWh ≈ $1.00–1.20/session (gas dominates ~30:1). Measured points override the affinity-law (P ∝ RPM³) estimates everywhere in Costs/What-If. Bonus while cycling speeds: note filter-gauge PSI at each RPM → free flow-restriction baseline (pairs with FlowVis if ever installed).
4. **Heater flow-switch test** — MODE=POOL at 1350 then 2600: fires? → documents the accidental interlock
5. **Switch-position mapping** — deck valve suction-vs-return ID + calibrated split positions, paint-pen marks photographed. **Fastest ID method — thermal touch test:** during a heat run (heater firing), touch both valve BODIES in their sleeves: the return valve carries heater-output water and is distinctly warm; the suction valve stays at pool temperature. Five seconds, nothing moved. Cross-checks: the "←FLOW" embossment on the right valve body (clear debris, photo both arrows — evidence, not proof; installers ignore them) and the drain-rate test's level-direction side effect (test 6).
6. **Spa drain-rate test** — return valve to full POOL, time level drop (1" ≈ 24 gal on ~38 ft² spa) → measured split-f
7. **Dye test** (optional) — return-side f cross-check via half-fade time τ ≈ 800/(f×Q)
8. **Waterfall+split drain verification** — from resting SPLIT, pad valve → WATERFALL briefly: does spa level fall? Confirms series topology + the POOL-valves-first rule (STOP test at first measurable drop; restore valves)
9. **SunTouch AUX/lights test** — press AUX 1/2/3, listen for relays, meter deck J-boxes → niche-light circuit hypothesis
10. **Left-timer load inventory** — SunTouch-breaker-off test + what dies with left lever (careful: master disconnect)
11. **Spa-level stability** (24 h at calibrated split) — ongoing monitor baseline
12. **Volume estimation** — record the inputs, factors, and derivation, not just the answer:
    - Pool inputs (per Justin, 7/25/26): 35' max length × 15' max width × 5' avg depth; bounding box 2,625 ft³
    - Freeform plan-area factor: 0.78–0.85 (chosen 0.80) for rock-cut corners/tapered ends → ~420 ft² × 5' × 7.48 gal/ft³ ≈ **15,500 gal (±15%)** — EST
    - Spa inputs: diameter + seat depth TBD (measure) → currently assumed **~800 gal** — EST
    - Total at split ≈ 16,300 gal
    - Editable fields for all inputs + factor so revised measurements recompute downstream (turnover, heat-rise, split-f targets)
    - Refinement path (flips badge to MEASURED) — **the 1-inch refill test:** mark the water line on a tile with painter's tape; let the level fall 1" (evaporation over a few summer days, or briefly run the submersible pump); shut off all other household water; read the house water meter; refill via hose/fill line exactly to the mark; read the meter again. **Gallons added ÷ 0.62 = true surface area (ft²)**; area × 1" ≈ gallons-per-inch (the constant every other level-based test uses); area × avg depth = volume. Note: this measures AREA precisely — avg depth (Justin's 5') remains the soft input, so quote volume as measured-area × estimated-depth. Alternative: trace plan area from the satellite photo at known scale.
13. **Fill-line trace** — the white PVC riser w/ brass valve by the fence (near heater) is believed a dedicated domestic fill line. Open briefly, find where water emerges at the pool; label the valve. (The rusty galvanized bib at the house wall = ordinary hose bib.)
14. **SMUD rate & EV-discount verification** — confirm the cost model's rate inputs against reality: (a) from Justin's SMUD bill, record the actual rate schedule name (TOD 5–8 p.m. expected) and the current $/kWh for each period — enter into the editable rate table with a MEASURED badge + bill date; (b) confirm the **EV discount is active**: the Tesla must be DMV-registered at the SMUD service address — check the bill for the midnight–6 AM discount line item, or verify via Justin's SMUD account; if absent, registering it is a free ~1.5¢/kWh on all overnight usage (pool + car); (c) note the rate season boundaries (Jun 1 / Oct 1) so the Costs tab can switch seasonally. Result: every $ figure in Costs/What-If traces to a dated bill, not a web lookup.
15. **Routine-care characterization (interview, not instrument)** — document the care regime as it actually operates; results populate the Maintenance tab's care calendar: (a) pool service: actual visit cadence (weekly? biweekly? seasonal?), scope of a standard visit (chemicals, brushing, baskets, filter?), how filter-cartridge cleaning is triggered and billed; (b) Justin's between-visit tasks: how often he actually empties skimmer baskets + pump strainer in normal vs needle-drop season. **Reference photo CAPTURED — but it's HISTORICAL (pre-surface-robot era, suggest title `skimmer-basket-full-historical`): baskets buried like this were the old normal, the upstream cause of the founding causal chain (choked basket → poor skimming → waterlogged needles sink → bottom + filter load → heater flow-switch opens → "heat only via waterfall"). The surface skimmer robot changed the system: it intercepts needles BEFORE they waterlog and sink — the state change that makes them expensive — relieving baskets, bottom robot, cartridge, and heater at once. Current basket load is much lighter; characterize the NEW cadence in the interview, and photo a current-typical basket for contrast (before/after pair for the Photos tab).** Peak needle-drop season remains a serious load — see test 16; (c) robot cycles: underwater cleaner — deploy trigger, runtime, recharge time, where it lives; skimmer robot — same; (d) anything else Justin does routinely that no one has written down.
